# Architecture

## Overview

The Inspection Management API is a FastAPI backend for road damage inspection workflows. Inspectors can register, log in, create inspection records, attach notes and optional base64 image data, and track AI-assisted classifications for damage type and severity. Admin users can view and manage inspections across all users.

The API is used by the inspection dashboard frontend and by authenticated API clients. The public API docs are deployed at [https://inspection-management-api.onrender.com/docs](https://inspection-management-api.onrender.com/docs). The companion frontend demo is deployed at [https://inspection-dashboard.vercel.app](https://inspection-dashboard.vercel.app).

The API exposes user-scoped inspection CRUD endpoints, admin-only cross-user endpoints, JWT authentication, rate-limited auth routes, a health check at `/health`, and Swagger docs at `/docs`.

## Tech Stack

- FastAPI for routing, dependency injection, OpenAPI docs, request validation, and background tasks.
- PostgreSQL support through SQLAlchemy and `psycopg2-binary`; local/demo defaults can use SQLite through `DATABASE_URL`.
- SQLAlchemy ORM for `User` and `Inspection` models.
- Alembic for versioned schema migrations.
- JWT authentication with `python-jose`.
- Password hashing with `passlib` and bcrypt.
- Groq vision classification through the Groq SDK for image requests.
- LangChain `ChatGroq` structured output for text-only classification.
- Pillow for image conversion, resizing, and JPEG compression before Groq calls.
- SlowAPI for auth endpoint rate limiting.
- pytest and FastAPI `TestClient` for API tests.
- Docker for deployment.

## Domain Model

`User` is defined in `app/models/user.py` with these fields:

- `id`: integer primary key.
- `email`: unique, indexed, required string.
- `hashed_password`: required string containing the bcrypt hash.
- `role`: required string with server default `"user"`.
- `inspections`: one-to-many relationship to `Inspection`.

`Inspection` is defined in `app/models/inspection.py` with these fields:

- `id`: integer primary key.
- `location_code`: indexed required string identifying the inspected location.
- `damage_type`: required string. Default is `pothole`.
- `severity`: required string. Default is `medium`.
- `status`: required string. Default is `reported`.
- `notes`: optional string.
- `image_data`: optional text field for base64 image data.
- `ai_rationale`: optional string explaining the AI decision.
- `ai_damage_type`: optional string storing the original AI damage classification.
- `ai_severity`: optional string storing the original AI severity classification.
- `is_ai_processed`: required boolean, default `False`.
- `reported_at`: required timestamp.
- `created_at`: required timestamp.
- `updated_at`: required timestamp updated on modification.
- `user_id`: required foreign key to `users.id`.
- `owner`: relationship back to `User`.

The AI override tracking pattern keeps two sets of classification values. `damage_type` and `severity` are the current editable values. `ai_damage_type` and `ai_severity` preserve the AI's original result. The `is_ai_overridden` SQLAlchemy `hybrid_property` is computed on read: it returns `False` until AI processing exists, then compares the current values against the AI values. This avoids storing a redundant boolean that could drift from the underlying fields.

## Auth

Users register through `POST /auth/register`. The password validator requires at least eight characters with uppercase, lowercase, numeric, and special-character content. Passwords are hashed with bcrypt before storage.

Users log in through `POST /auth/login` using `OAuth2PasswordRequestForm` form data. `login_user()` verifies the password and returns a bearer token generated by `create_access_token()`. The JWT contains the user id in `sub`, uses the configured `SECRET_KEY`, `ALGORITHM`, and `ACCESS_TOKEN_EXPIRE_MINUTES`, and is decoded on later requests.

Authenticated routes depend on `get_current_user()` from `app/core/deps.py`. It reads the bearer token via `OAuth2PasswordBearer`, decodes the JWT, loads the user from the database, and raises `401` if validation fails.

Admin authorization is handled by `require_admin()`, which wraps `get_current_user()` and requires `current_user.role == UserRole.admin`. Admin endpoints live under `/admin` and currently include:

- `GET /admin/inspections`
- `PUT /admin/inspections/{inspection_id}`
- `DELETE /admin/inspections/{inspection_id}`

The regular `/inspections` endpoints are scoped by `Inspection.user_id == current_user.id`, so non-admin users cannot read, update, or delete another user's inspections through those routes. If `ADMIN_EMAIL` is configured, `login_user()` promotes that matching user to admin on login.

## AI Classification Pipeline

Creating an inspection through `POST /inspections` writes the database row first and returns `201` immediately. The router then schedules `process_inspection_with_ai()` as a FastAPI `BackgroundTask`, passing the new inspection id.

The background task opens its own `SessionLocal` database session because the request-scoped session is closed after the HTTP response. It reloads the inspection, skips AI work if both `notes` and `image_data` are empty, calls `AIService.classify_inspection()`, then writes the result back to:

- `damage_type`
- `severity`
- `ai_damage_type`
- `ai_severity`
- `ai_rationale`
- `is_ai_processed = True`

There are two AI code paths in `app/services/ai_service.py`:

- Image path: if `image_data` is present, the service compresses the base64 image to RGB JPEG, resizes the longest side to at most `1024px`, uses JPEG quality `75`, and calls Groq directly with `AsyncGroq`. It prompts for JSON and parses the returned content into `AIClassification`.
- Text-only path: if no image is present, the service uses LangChain `ChatGroq(...).with_structured_output(AIClassification)` and invokes it with the inspection notes.

The code uses the Groq SDK directly for vision because the implementation notes state that `langchain-groq` does not pass image content properly. LangChain remains in use for text-only classification because structured output maps cleanly into the `AIClassification` Pydantic model.

## Testing

The tests are API-level tests using FastAPI `TestClient`; they do not mock the service layer or ORM calls. That matters because the tests exercise routing, validation, auth dependencies, SQLAlchemy queries, relationships, and database writes together.

In the current checkout, `tests/conftest.py` sets `DATABASE_URL=sqlite:////tmp/inspection_test.db`, removes any old test database file, imports the SQLAlchemy models, and bootstraps the schema with `Base.metadata.create_all(bind=engine)`. Production uses Alembic migrations, but the current pytest bootstrap creates the schema directly from model metadata.

`docker-compose.yml` includes a PostgreSQL 15 service and runs the API/tests against `postgresql://postgres:postgres@db:5432/taskdb` when using the Compose setup. The current GitHub Actions workflow in this working tree runs migrations and tests against SQLite, not PostgreSQL.

The test suite covers registration and login, invalid credentials, authenticated inspection CRUD, user data isolation, validation errors, filtering, pagination, sorting, admin role enforcement, and admin cross-user operations. Smoke tests cover `/health` and an auth-to-inspection round trip.

## Deployment

The backend is containerized with Docker. The `Dockerfile` installs dependencies, copies the repository into the image, sets `PORT=8000`, and starts with:

```bash
alembic upgrade head && uvicorn app.main:app --host 0.0.0.0 --port ${PORT}
```

That means Alembic migrations run before Uvicorn starts. `start.sh` contains the same startup sequence for environments that use the script directly.

Render deployment uses the Docker image and should provide runtime configuration through environment variables. Relevant settings are loaded in `app/core/config.py`:

- `DATABASE_URL`
- `SECRET_KEY`
- `ALGORITHM`
- `ACCESS_TOKEN_EXPIRE_MINUTES`
- `ADMIN_EMAIL`
- `ALLOWED_ORIGINS`
- `GROQ_API_KEY`
- `LANGSMITH_TRACING`
- `LANGSMITH_API_KEY`
- `LANGSMITH_PROJECT`
- `RATE_LIMIT_ENABLED` for SlowAPI behavior

`app/database.py` normalizes Render-style `postgres://` URLs to SQLAlchemy's `postgresql://` form. If no `DATABASE_URL` is provided, the code defaults to `sqlite:////tmp/inspection_demo.db`, which is demo-safe but not a persistent production database.

## Known Limitations

- Groq API calls can hit provider rate limits or fail; the background task logs exceptions and rolls back the AI update, but it does not retry.
- Images are stored and accepted as base64 text, then compressed to a maximum `1024px` longest side and JPEG quality `75` before vision classification. There is no explicit request-level upload size enforcement in the FastAPI schema.
- There is no audit log table for inspection edits, admin changes, AI classifications, or human overrides.
- Current background AI processing uses in-process FastAPI background tasks, not an external durable queue.
